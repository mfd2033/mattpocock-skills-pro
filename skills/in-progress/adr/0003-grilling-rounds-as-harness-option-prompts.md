# Deliver `grilling` rounds as harness option prompts, from a separate model-invoked skill

`grilling` prints each round as numbered text and the human answers by typing. Typing every answer is the slow half of a long interview, and every harness in use ships a structured-choice prompt tool (CodeBuddy's `ask_followup_question`, Claude Code's `AskUserQuestion`) that takes a question plus a bounded option list. We add a presentation layer that delivers each round through that tool, so an answer is a click or a typed override. It lives in its own model-invoked skill, `grilling-pro`, reached by two thin wrappers (`grill-me-pro`, `grill-with-docs-pro`), rather than copied into both or folded into `grilling` itself.

## Considered Options

- **Change `grilling` in place.** Cheapest, and it would upgrade `grill-me`, `grill-with-docs`, `triage`, `wayfinder`, and `improve-codebase-architecture` at once. Rejected because it spends the behaviour change on every skill that runs the primitive whether or not its user wants a click surface, and it makes the two `-pro` wrappers redundant: the reason to ship a separate name is that the text round stays the default.
- **Inline the rule in both wrappers.** Keeps the artifact count at two, but writes one meaning in two places, which the repo's single-source-of-truth rule forbids, and leaves the two copies to drift.
- **Fork `grilling` into a variant primitive.** Avoids the presentation/client split entirely, at the cost of copying the primitive's rounds, frontier, and design-tree content into a second home.

## Consequences

- `grilling-pro` must be **model-invoked**, because both wrappers have to reach it and a user-invoked skill can reach nothing. Its description is therefore always loaded, so it has to stay narrow: it names the job (present a `grilling` round as option prompts) and says the two wrappers reach it, which keeps the model from reaching for it in place of `grilling` on a plain "grill me".
- The tool takes at most 4 questions per call and 4 options per question, while a round is every question on the frontier. A round longer than 4 questions therefore spills into consecutive calls with continuous numbering: the round is the sequence of calls, not one call. "Consecutive" means one call per turn, for the reason in the next point.
- **Consecutive calls cannot be batched into one turn.** Measured on CodeBuddy: two `ask_followup_question` calls in one message both report `Questions displayed`, but only the first form's answers return; the rest are dropped with no error, and the model reads the round as finished and never re-asks. A round longer than four questions therefore costs one human turn per four questions, and each call may only be issued after the previous call's answers have arrived. Batching is the failure mode to avoid, and because it fails silently, the skill has to state the per-turn rule rather than leave it to the harness.
- The tool's name is harness-specific, which collides with the deliberate removal of Claude Code's tool names in 1.2.3 (see `CHANGELOG.md`, #781). The rule resolves it by writing the capability as the instruction and naming `ask_followup_question` and `AskUserQuestion` once as examples, accepting the wording cost for a higher hit rate on the harnesses actually in use. A harness with no such tool falls back to `grilling`'s text round instead of failing.
- A typed answer still counts, and overrides the picks. The option list is a shortcut, never a cage.
- All three skills land in `in-progress/`, so none of this ships in the plugin yet, and this ADR records a beta decision. Promotion is where the harness-naming choice has to be re-argued against the 1.2.3 convention, since promotion is permanent in a way a beta bucket is not.
